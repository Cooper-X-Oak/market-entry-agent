## 3. 业务语义必须成立

本次产品范围：阀门、管件、钢管、卫生级阀门管件、流体设备。潜在客户角色按证据识别，可包含经销商、库存商、工程承包商、设备集成商、终端用户。

地区：喀山按城市范围；马来西亚、印尼、哈萨克斯坦、越南按国家范围。地域层级必须结构化保存，不能只靠提示词约束，也不能把喀山自动扩大到俄罗斯全国。

| 对象 | 语义约定 | 不允许的推断 |
| --- | --- | --- |
| 委托方 | 提出研究需求的主体；本案例沿用已报告的温州和平广告 | 从其名称或网站推断工业制造能力 |
| 供应方 | 实际供货主体，可缺失；能力判断需要可追溯资料 | 默认等于委托方；从研究产品清单生成产能、认证或交付承诺 |
| 研究范围 | 产品、地区、客户角色及筛选条件 | 当作供应方能力证明 |
| 目标客户 | 经研究获得的企业及角色 | 官网提到产品就等于有明确采购需求 |
| 用户陈述 | 用户输入及其来源，可用于任务定义 | 未经验证变成外部事实 |
| 假设 | 待研究、待验证的判断 | 直接进入已支持的事实或行动承诺 |
| 证据 | 可定位到来源/快照/摘录的记录 | 随机 UUID、仅有格式而不存在的 ID |

必须支持“供应方未知的客户研究”：可以判断目标的产品相关性、客户角色、地域和公开联系路径；供应方适配结论应明确为未评估或信息不足。只有供应方能力相关步骤受影响，不能因此阻断所有客户研究。

## 5. 原子任务清单

### A00：建立当前链路与失败基线

输入：当前源码、既有中间格式、失败目录和 Mission 标识。

工作：定位创建入口 → compileMission → Connector/context → Provider → 校验 → 持久化 → Workflow/投影 → 导出；记录对应文件、函数、类型和事务边界。重建 Compiler 当次可取得的输入证据集合及错误输出，核对取消现状。

验收：形成一张当前链路映射及事实/假设表；可取得的失败样本能够离线触发相同错误。敏感数据脱敏，保留可核验哈希。无法取得现场不阻塞用明确标记的回归样本推进。

### A01：纠正业务主体与研究输入契约

依赖：A00。

工作：在实际输入契约及规范化逻辑中区分委托方、供应方、研究范围；表示供应方缺失及能力匹配未评估。用户已明确的产品、城市/国家边界必须由确定性逻辑保留。检查旧 companyName/companyWebsite 的真实语义，不能一律重解释为供应方或委托方。

验收：委托方广告网站不会触发对其工业制造能力的肯定判断；无供应方仍可创建客户研究计划；喀山不会扩大；历史输入经兼容路径读取，歧义信息明确标记。若必须变更存储，准备兼容迁移并在隔离环境验证，不擅自迁移远端。

### A02：定义并纠正 Mission Compiler 的职责

依赖：A01。

职责：把用户需求转换为可执行研究计划，包括范围、约束、目标角色、缺失信息和下一步研究任务。Compiler 不把尚未研究的内容包装成已获证据支持的业务结论。

工作：追踪 proposedClaims 的消费者，选择最小兼容修复。如果当前流程确实先取得证据，可保留基于这些证据提出判断的能力；没有证据时输出需求或待验证假设，不能要求模型生成“有证据事实”。不直接删除字段导致下游失效，也不把空 evidenceRefs 偷换成“已有支持”。

验收：无证据、仅用户输入、有证据三个输入情境均有明确输出及下游路径；无证据能完成任务编译但不能产生已支持的事实；供应方不足只影响相关能力步骤。测试经过实际 Compiler/context/validator 路径。

### A03：纠正证据选择与引用解析

依赖：A00、A02。

工作：程序生成并持久化证据 ID；模型只选择本次上下文允许引用的集合。可复用现有真实 ID，或使用程序生成的短引用键并确定性映射到真实 ID，禁止按字符串相似度猜测修复。

校验顺序：结构合法 → 属于允许集合且访问范围合法 → 对应证据/快照存在 → 内容能够支持该判断。来源属于历史任务不必一律禁止，但必须经明确的复用与授权路径进入本次上下文。UUID 格式校验不能代替以上检查。

格式或集合错误属于输出契约失败；存在合法引用但内容不足时，拒绝其成为已支持判断，按业务契约转待验证或明确失败，不能静默删除引用后保留结论。

验收：覆盖非法 UUID、合法但不存在的 ID、未授权跨任务引用、合法但不支持判断的证据、有效引用、空集合。持久化后能沿 Claim → Evidence → Snapshot/Source 重新读取。不得只测辅助解析函数。

### A04：固定 Provider 边界和错误分类

依赖：A00；与 A02/A03 集成验收。

工作：保留原业务 Zod 校验，复核现有完整 Schema 传输修复。区分传输/限流/暂时性服务错误、Provider 请求配置错误、输出格式错误、引用错误、业务前置条件缺失、超时、取消。使用项目兼容的类型化错误传到实际 Activity 边界。

验收：所有本次调用链使用的实际 Schema 能离线走通转换路径；错误类型未被通用 catch 包装丢失；strict:false 不被报告成服务端严格保证；不默认切换 Mock。已有 Target Ranker 通过结果保留其单项边界。

### A05：纠正重试所有权

依赖：A04。

工作：列出 SDK、Provider wrapper、Activity、Workflow 每层现有重试。一次逻辑步骤只由一层负责暂时性 Provider 故障的自动重试，其他层不得乘法放大。业务输出/引用校验失败本轮默认不自动重试；不新增模型自修复循环。

默认执行策略：暂时性错误最多 3 次总尝试（含首次），遵循可取得的 Retry-After，设置单次超时和总截止时间；实际配置数值写进契约。配置错误、输入缺失、输出校验失败直接结束本次步骤。取消后不再派发新请求。写入故障重试优先复用已安全保存且通过校验的结果，不无条件重新付费生成。

验收：同一非法引用只触发 1 次业务生成；一次暂时故障后成功为 2 次；持续暂时故障最多 3 次。验证实际 SDK 配置与 Temporal 错误映射/重试策略，不能只给函数传一个 retry=false。区分逻辑执行、Activity 尝试和真实 HTTP 尝试。

### A06：让执行事实独立留存

依赖：A00、A04。

工作：将执行审计持久化与业务结果事务分开。请求发起前独立记录 intent/started，结束后记录结果、错误和可取得的用量；业务结果写入仍保持必要的原子性。不要让数据库事务跨越完整网络等待。

至少记录：Mission/Run/Activity 标识、逻辑调用 ID、Activity 与 HTTP 尝试编号（不可取得则注明）、模型、开始/结束时间、请求状态、Provider request ID（如有）、用量、费用及其来源、错误分类、输入/输出的安全引用或哈希、代码/契约版本。密钥不得入日志。

崩溃窗口处理：有 started 无结束记录时标为待核对/未知，不能判零调用或零费用。审计起始记录写失败时不新发付费请求；结束记录写失败保留可恢复线索并如实报错。复用现有设施，避免引入与本任务无关的消息平台。

验收：模拟 Provider 成功后业务校验失败、业务事务回滚、进程在结束记录前中断；已发生的调用仍可查到，未知用量不记零。审计幂等键区分实际新尝试，不能把多次收费覆盖为一条成功记录。

### A07：纠正业务提交幂等性

依赖：A03、A06。

工作：按实际逻辑操作建立稳定提交标识和项目适用的去重保障。Activity 重放、提交成功但响应丢失、投影重放不能产生重复 Claim、Target、行动卡或重复状态事件。不能宣称因此实现 Provider 收费的 exactly-once。

验收：注入提交后响应丢失并重放，业务对象只保存一份；执行审计仍保留真实尝试；校验失败不会留下半套成功业务数据。使用实际持久化边界测试，不仅测内存集合去重。

### A08：纠正失败、取消及状态投影

依赖：A04、A05、A06。

工作：先明确业务 Mission 状态、Workflow 状态、Activity 状态、Provider 请求状态各自的权威来源。给失败、重试耗尽、取消请求、工作流关闭、外部请求未确认结束建立映射及收尾责任。

取消信号应沿实际运行链传递到可中止的请求；若无法确认 Provider 服务端终止，保留未知，客户端 abort 不代表零费用。取消后到达的结果不能推进业务成功；允许补记审计用量。外部取消工作流也必须有可恢复的业务状态收敛路径，不能仅依赖正常业务事件或可能被取消打断的 finally。

验收：分别覆盖调用前取消、请求中取消、校验失败、重试耗尽、完成与取消竞态、重复/乱序投影事件。Mission 不永久停在 running，终态不被迟到事件覆盖；声明并验证有界收敛时间。旧 Mission 通过正式恢复/对账路径处理或明确待处理，禁止手工改库伪造通过。

### A09：纠正读取与导出

依赖：A01、A03、A06、A08。

工作：导出仅从本次持久化数据构造，记录 Mission、运行/契约版本及业务状态；提供核对对象归属和引用的方法。明确失败现场与有效业务成果的区别。审计敏感字段不进入面向业务用户的导出。

修复中文名称响应头问题，采用标准兼容的下载文件名处理，同时处理引号、换行和路径字符。不能要求用户改英文名绕过问题。

验收：中文任务名直接经 API 成功下载；解包内容与重新读取的本次数据一致；失败 Mission 可导出且不会显示业务成功；没有其他任务对象混入。引用可解析，目标为零明确记零。

### A10：验证一次最短链路并完成交付

依赖：A01—A09。

先在隔离环境经现有应用入口、Worker/Workflow、原业务校验、实际持久化与导出跑最短集成场景：无供应方的需求 → Compiler → 证据/判断 → 目标与公开联系路径 → 待审核行动卡 → 保存 → 重新读取 → 导出。复用真实组件；外部 Provider 使用明确标识的受控响应进行故障注入，测试数据不得进入真实业务产物。

基于同一路径完成非法引用、取消、事务回滚与重复执行的关键失败场景。局部单测通过不能替代实际模块交接验证。

上述工程门槛通过后，可使用已授权真实 Provider 做一次实际 Compiler 验证。输入只含真实已知信息，核验其输出语义、证据集合及记录留存，不仅看 HTTP 200。若因真实失败需要重复调用，应先定位和修复，不原样循环。

最终生成部署候选、完整实际文件清单、构建对应关系、受影响服务、数据兼容措施和回退步骤。不得沿用已经过时的三文件清单。若新部署缺少授权，只在所有这些工作完成后集中说明具体待批准动作；其余工程结果照常交付。

## 6. 核心验收矩阵

| 场景 | 必须观察到的结果 |
| --- | --- |
| 无供应方、有明确客户研究需求 | 计划可执行；能力匹配未评估；不虚构供货能力 |
| Compiler 无证据 | 可以编译需求；不能生成已获证据支持的事实 |
| 未知/非法 evidenceRef | 拒绝作为成功结果；不原样自动重试；失败审计存在 |
| 引用存在但不支持判断 | 不升级为已支持事实；有明确待验证或失败状态 |
| 合法充分引用 | 写入、重读、导出均能追溯到来源 |
| Provider 暂时故障 | 总尝试有界；各层计数可解释 |
| 业务提交回滚 | 不留半套成果；调用事实仍存在 |
| 提交后响应丢失并重放 | 业务结果不重复；执行尝试不被抹掉 |
| 请求进行中取消 | 不继续派发/推进业务；状态收敛；服务端未知保留未知 |
| 中文名导出 | 无需改名，现有 API 可下载并核对内容 |
| 历史任务/旧输入读取 | 不崩溃、不静默改变主体含义或事实可信等级 |

测试量按这些风险决定，不以测试数量或覆盖率百分比作为完成指标。不要求与实现一一对应的空泛测试。若发现后续模块仍阻塞上述明确链路，可增加有证据支持的最小原子修复任务；不得无限扩展成其他项目治理。
