## 实际执行与证据边界

1. 原 SDK-Zod 路径无法把真实 Target Ranker 的输出结构转为严格 JSON Schema。脱网诊断记录 `outboundRequests=0`，报错指向 `result.targets[].website` 的 optional / nullable 兼容问题。这不推翻此前简单 Schema 的 CPA 三模型 PASS，但证明该 PASS 不覆盖真实 Target Ranker 输出结构。
2. 仅在实验执行器中增加显式非严格 JSON Schema 传输，两组共用该适配，仍由原 Zod Schema 解析响应。未修改应用 Provider 或业务 Schema，没有部署。
3. 适配后日志显示 `RU-TA no-search 1 completed`，随后进入 `RU-TA search 1 started`。该日志最多说明执行器报告首个不搜索组完成；最终完整 JSON 没有保存，不能据此发布目标排名、引用正确率或业务通过结论。
4. 搜索组长时间未返回可比较结果后，本轮停止扩批，并对独立实验进程发送 SIGTERM。随后观察到该进程已不存在，但本地回传连接仍未结束；只关闭了已识别的实验 SSH 客户端。应用 Worker 和服务器生命周期未作变更。
5. 两个结果 JSON 文件均为空，分别保留原位；第二次外层执行记录退出码为 `-1`。第一次外层记录的 `exitCode=0` 不代表实验成功，另有说明文件纠正其解释。此次无法确认最终结果丢失的具体环节，不能把它归因为 CPA 本身、搜索无价值或模型质量差。

因此，没有完整配对、没有已保存的可审阅排名，也没有足够数据计算质量差、排序稳定性、增量引用率或真实耗时差。其余四个市场未取得可审阅的配对输出。已发生的搜索和模型费用无法从回传结果汇总，金额与 token 合计均记为未知，不记为零。

## 本轮决定与后续边界

- 保留正式目标排序的默认搜索；此次不作删减决定。
- 默认 Provider 的真实业务 Schema 兼容问题仍待单独解决；实验内适配不能当作生产修复。
- 执行器已补入 `--jsonl` 逐组保存，以及明确组超时后停止扩批的入口，防止只能在整轮末尾保存。补入后的代码本轮未重跑，不能声称结果回传已修好；实际执行使用的脚本副本另行归档。
- 恢复消融时，先取得并保存一个市场的一对完整结果，再扩展其余市场和重复轮。只有质量、来源支持与成本记录齐全，才能讨论关闭额外搜索或改为按未知项触发。

本轮 Bootstrap 定向源码类型检查通过；常规包级检查受依赖准备策略及既有编译声明不一致影响，详见统一入口。未执行 Bootstrap 数据库运行、登录、Agent Browser、完整 BM1、部署或服务器生命周期验收。
