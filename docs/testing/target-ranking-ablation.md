# 目标排序额外搜索消融规约

本规约定义带前置 Schema 传输适配的局部实验。当前实施状态和验收结论只在 [当前状态与 BM1 验收入口](README.md) 维护；这里不替代 BM1 全链验收，也不能证明默认生产 Provider 已修复。

## 业务范围

使用用户提供的温州出海营销代理业务：服务温州为主的制造企业，研究阀门、管件、钢管、卫生级阀门管件和流体设备的相关客户。市场分别为俄罗斯鞑靼斯坦共和国、马来西亚、印度尼西亚、哈萨克斯坦、越南。进口商、经销商优先，兼顾 EPC 与工业终端。

每个市场独立形成候选与来源样本。官网描述能够支持企业角色、产品或行业关联，不能直接证明当期采购意向、中国进口记录、新供应商意愿或某家温州工厂的认证适配。

首轮输入是按该业务需求整理的公开来源研究上下文，不是从已完成 BM1 的 Live Mission 导出。只保留必要官网短引文、研究转述与来源链接；输入证据 hash 对应保存的研究摘录，不代表原站完整网页 hash。尚未提供的企业名称与官网明确标为未知；Schema 所需的 `.invalid` URL 仅作缺失值占位，不作为真实企业或证据。

## 唯一变量与执行方式

| 项目 | 搜索组 | 不搜索组 |
|---|---|---|
| Skill | 当前 `targetRankerSkill` | 仅覆盖 `planQueries: () => []` |
| 模型 | `gpt-6-astra` | 相同 |
| 指令、Schema、预算、权限、上游候选 | 原有设置 | 相同输入的独立深拷贝 |
| Schema 传输 | 显式 `json-schema-nonstrict` 实验适配；保留原 Zod parse | 相同 |
| AgentRunner / ContextBuilder | 使用现有实现及 repository 分支 | 相同 |
| 额外搜索 | 当前三个查询，每次至多四个来源，保留原有证据停止条件 | 零次 |
| 业务记录写入 | 无 | 无 |

执行器为 `scripts/target-ranking-ablation.mjs`。它通过 Worker 的依赖解析路径使用现有包，不调用 `rankTargets()` Activity，不创建数据库客户端或 Object Storage 客户端。`toolCompleted` 把搜索证据放入内存 repository，确保新增摘录进入原有 ContextBuilder 的模型输入。

首次沿用原 SDK-Zod 路径的实跑，在将真实 `targetRanker` 输出 Schema 转换为请求结构时即失败，涉及 `website` 为 optional 但不是 nullable；尚未取得可用于比较的真实排序输出。原始空结果与错误记录保留，独立实验进程已停止。这是后续增加传输适配的原因，不能解释为不搜索组业务质量差或两组等效。

执行器新增显式 `--schema-transport json-schema-nonstrict`，仅在独立实验进程内通过 transport facade 使用非严格 JSON Schema 传输；搜索组与不搜索组采用同一适配，响应仍交给原业务 Zod Schema 解析。应用 Provider、业务 Schema 和部署不因此改变。官方严格结构化输出要求字段全部为 required，可通过与 `null` 联合表达可选语义；本实验的非严格传输不能沿用严格模式的 Schema 遵循保证，原 Zod parse 失败必须保留为失败。[官方结构化输出说明](https://developers.openai.com/api/docs/guides/structured-outputs)

适配后先执行首个不搜索组并检查真实输出，确认能取得可解析、可对照候选与证据的结果；收不到可验证输出就停止后续搜索和剩余组，不消耗完整实验预算来重复前置失败。通过这一步后，每个市场首次搜索取得结果即冻结；后续重复轮重放相同成功结果或失败记录，并交替两组顺序以减少顺序影响。新来源和快照 ID 只存在于实验内存，不冒充应用记录。既有证据顺序用于近似数据库时间顺序，保留最新 240 条，再优先安排关联证据；这项近似需保留在实验记录中。

执行器限制 1–5 个市场、每组 1–3 次重复、每个组设置 5 分钟计时上限。首轮原定 5 个市场、两组各两次，共 20 次排序调用，最多 15 次额外搜索；这是上限，不是必须跑满的数量。SDK 重试请求不会自动扩展实验次数；失败与超时保留为结果，不自动更换模型。当前源码收到明确的组超时结果后停止扩批，等待审阅；事件循环阻塞或回传通道故障仍可能使内部计时与正常退出保存失效。

`--jsonl` 逐组输出 `event=arm` 记录，最后输出 `event=final`。文件模式每组同步保存；标准输出模式仍依赖调用方持续接收、保存完整 JSON 行。缺少 final 表示整轮未完成，只有已保存的完整配对可用于对照。`SIGTERM` 会请求中断当前组，等待其退出后保存；这不是强制终止下的数据完整性保证。该逐组保存入口在本轮回传失败后补入源码，尚未重跑验收。

在已获授权、已有环境注入 Provider 配置的进程中使用：

```text
node scripts/target-ranking-ablation.mjs --input <input-snapshot.json> --output <new-results.jsonl> --schema-transport json-schema-nonstrict --jsonl
```

`--stdio` 用于通过进程输入传递同一 Snapshot 并取回 JSON；本次仍须显式携带 `--schema-transport json-schema-nonstrict`。它支持在既有 Worker 内执行独立实验进程，无须部署或重启应用。执行器不读取任何 env 文件；本机受保护的 Provider 文件不得读取、复制或上传。输出文件拒绝覆盖已有结果，适配前后的运行记录分别保留。

## 评价与结论

每次运行的 method 必须披露 Schema 传输模式、原 SDK-Zod 前置失败、两组共用的适配、原 Zod parse、首个不搜索组的输出检查及实际停止位置。只有同一适配下取得完整有效且已保存的配对，才能讨论额外搜索的影响。具体运行结论见 [2026-09-05 首轮记录](runs/目标排序消融-20260905.md)。

自动计数只称为结构检查：Runner 是否成功、工具是否失败、候选之外的组织或网站、未提供的证据 ID、引用是否在模型上下文可见、新增证据实际被引用的数量。模型自报的置信度或覆盖率不作为业务质量分数。

业务审阅必须对照具体目标、引用摘录和原始来源，判断身份与市场覆盖、产品适配、角色、需求、采购责任和行动建议是否被支持。区分直接支持、合理推断、未知、无依据和矛盾；名称别名或集团域名误报需要逐项解释。排序改变本身不等于提升，最终应看它是否改善了下一轮研究或客户选择。

成本分开记录：真实外部搜索与网页请求次数、排序调用 token、可获取的搜索 token、模型耗时及首次真实搜索耗时。重复轮的搜索缓存只用于稳定输入，其接近零的耗时不能代表正式运行的搜索成本。Provider 当前不返回可用计价，因此金额为 `null`，不得描述为免费。

局部样本不能证明全市场覆盖、Top 10 交付能力或完整 BM1 有效性。即使带适配的实验取得有效结果，也不能证明默认生产 Provider 的 SDK-Zod 路径已修好，或把结果直接外推到未经适配的生产流程。需要多个代表性案例和证据审阅共同支持，才可将某个实验选择提升为默认流程；本规约不自动关闭正式 `targetRankerSkill` 的搜索。
